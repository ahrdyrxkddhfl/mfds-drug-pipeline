# 데이터 발견 사항과 판단 기록

실데이터를 적재하고 프로파일링하면서 발견한 사실, 확인 방법, 그에 따른 설계 판단을 기록한다.
README는 이 문서에서 핵심만 골라 쓴다.

- 기준 데이터: 의약품 제품 허가정보 42,980건, 의약품 회수·판매중지 정보 958건
- 사용 API: `DrugPrdtPrmsnInfoService08/getDrugPrdtPrmsnInq08`, `MdcinRtrvlSleStpgeInfoService05/getMdcinRtrvlSleStpgelList05`
- 확인 방법: raw 테이블의 JSONB를 `jsonb_each_text`로 펼쳐 필드별 결측·고유값을 집계

---

## 1. 식별자

### 업체 식별자가 여러 개로 분산되어 있다

| 필드 | 고유값 수 |
|---|---|
| ENTP_SEQ | 800 |
| ENTP_NO | 706 |
| ENTP_ENG_NAME | 604 |
| BIZRNO (사업자등록번호) | 602 |
| ENTP_NAME | 596 |

같은 회사가 ENTP_SEQ 여러 개로 흩어져 있다. 사업자등록번호를 업체 통합 키로 쓰고, 허가 42,980건 전부 값이 있어(null 0, 빈 값 0) `company.bizrno`를 NOT NULL로 둔다.
업체명이 사업자번호보다 적은 것은 같은 이름을 쓰는 사업자가 있다는 뜻이다. 업체명은 키로 쓰지 않는다.

### ITEM_SEQ는 허가 PK로 안전하다

42,980건 모두 고유하다. 단, 허가 갱신 시 새로 발급되므로 제품 식별자로는 쓸 수 없다(4절).

### PRDLST_STDR_CODE는 ITEM_SEQ와 전 건 동일하다

42,980건 중 다른 값 0건. 중복 컬럼이므로 `permit`에 저장하지 않는다.
지금 같다고 앞으로도 같다는 보장은 없으므로, 동일성은 검증 규칙으로 매 배치 확인한다.

## 2. 값의 형식

### 결측 표기가 필드마다 다르다

| 소스 | 필드 | null | 빈 문자열 |
|---|---|---|---|
| permit | BIG_PRDT_IMG_URL | 0 | 21,121 |
| permit | EDI_CODE | 22,008 | 0 |
| recall | STD_CD | 0 | 182 |
| recall | RTRVL_CMMND_DT | 118 | 0 |

같은 API 안에서도 필드마다 결측 규칙이 다르다. `clean_text`에서 둘을 None으로 통일한다.

### 날짜 형식은 두 가지뿐이다

숫자를 9로 치환해 패턴별로 세면 허가일·취소일·회수일은 전부 `99999999`(8자리), `RTRVL_CMMND_DT`만 `99999999999999`(14자리)다.
`parse_date`는 이 두 형식만 받고 나머지는 예외로 알린다. 형식이 바뀌었다는 신호를 추측으로 삼키지 않기 위해서다.

### 취소 상태와 취소일은 완벽하게 정합한다

| CANCEL_NAME | 건수 | 취소일 있음 |
|---|---|---|
| 정상 | 35,268 | 0 |
| 유효기간만료 | 4,620 | 4,620 |
| 취하 | 2,787 | 2,787 |
| 폐업 | 258 | 258 |
| 행정(취소) | 25 | 25 |
| 취소 | 22 | 22 |

현재 위반 0건이지만 원천이 깨지는 순간을 잡기 위해 검증 규칙으로 둔다.
`행정(취소)`와 `취소`는 같은 뜻인지 근거가 없어 합치지 않고 원본 값을 유지한다.

### 성분 수와 성분명의 결측이 일치하지 않는다

`ITEM_INGR_CNT` null 66건, `ITEM_INGR_NAME` null 81건. 원본 성분 수를 `permit.ingr_cnt_raw`로 보존하고, 분해한 성분 수와 대조하는 검증 규칙을 둔다.
성분명은 `/` 구분이며, 같은 성분이 반복 나열되는 사례(Fentanyl/Fentanyl)가 있어 순서와 중복을 그대로 보존한다.

## 3. 회수 데이터

### 레코드마다 래퍼가 한 겹 더 있다

회수 API는 레코드를 `{"item": {...}}`로 감싸 보낸다. 허가 API에는 없다.
래퍼는 데이터가 아니라 응답 포장이므로 추출 단계에서 벗겨, raw의 payload 깊이를 소스와 무관하게 통일한다.

### 회수 건 식별자가 없다

958건에 ITEM_SEQ는 849개. 같은 품목이 여러 번 회수된다.

| 자연키 후보 | 고유 조합 수 |
|---|---|
| (ITEM_SEQ, RECALL_COMMAND_DATE) | 950 |
| (ITEM_SEQ, RECALL_COMMAND_DATE, RTRVL_RESN) | 954 |

세 필드로도 4행이 겹친다. 겹치는 3개 그룹(3행, 2행, 2행)은 모두 **같은 페이지 안에 id가 연속**으로 있어, 수집 중 순서 밀림이 아니라 원천이 같은 행을 여러 번 준 것이다.
목록 API 기준으로 내용이 완전히 같다(변환 시 3건 모두 info로 기록).

상세조회 API의 응답 모델에는 목록에 없는 `MNFCTUR_NO`(제조번호)가 있다. 원본에서는 제조번호로 구분되는 별개 행일 가능성이 있다(미검증).
그래서 1행으로 합치되 원 행 수를 `source_row_count`로 보존한다. 합친 뒤 954건.

### 회수의 44%가 허가정보와 연결되지 않는다

회수 958건 중 ITEM_SEQ가 허가정보에 있는 건은 534건(55.7%).

세운 가설과 검증 결과:

| 가설 | 결과 |
|---|---|
| ITEM_SEQ 표기 차이(공백 등) | 기각. 양쪽 모두 결측·빈 값 0, 전부 9자리 숫자 |
| 오래전 취하된 품목이 허가정보에서 빠짐 | 기각. 미연결 건이 2023년 34, 2024년 159, 2025년 126, 2026년 105로 고르게 분포 |
| 구버전 API가 의약외품을 섞어 보냄 | 기각. 05 의약품 목록조회로 바꿔도 동일한 958건 |
| 회수 API의 품목 범위가 허가 API보다 넓음 | 유력. 미연결 샘플 제품명이 소독용에탄올, 치약, KF94 마스크, 탄력붕대, 복분자, 당귀 등 |

마지막 가설의 근거는 제품명뿐이고 회수 API에 품목 구분 필드는 없다. 그래서 파이프라인이 품목 종류를 분류해 넣지 않는다.
`recall.item_seq`에 permit으로 가는 FK를 걸지 않는다. 걸면 424건이 적재되지 않는다. 연결 여부는 조회 시 LEFT JOIN으로 판단하고, 미연결 건수는 info로 기록한다.

### 두 날짜 필드의 의미를 확정할 수 없다

포털 설명에는 제공 항목으로 승인일자와 회수명령일자가 있지만, 응답 명세에는 필드별 설명이 없다.
`RECALL_COMMAND_DATE`는 항상 값이 있고 `RTRVL_CMMND_DT`는 118건이 비어 있다. 의미를 단정하지 않고 원본 필드명을 살린 컬럼명(`recall_command_date`, `rtrvl_cmmnd_date`)을 쓴다.

## 4. 제품 동일성

허가 갱신 시 ITEM_SEQ가 새로 발급되므로, 정규화한 제품명과 사업자번호로 같은 제품을 묶는다.
정규화: NFKC(㎍ → μg), 괄호 분리, 표기 통일(밀리그람 → 밀리그램), 공백 제거, 소문자화.

### 1차 규칙: 과병합 발견

1차 규칙은 `수출용`이나 숫자가 든 괄호만 남기고 나머지 괄호를 버렸다. 결과는 허가 151건이 기존 제품에 합쳐짐, 검토 대상 20개.
합쳐진 제품 샘플에서 과병합이 나왔다.

- `아이델라주(티옥트산)` / `아이델라주(티옥트산)(바이알)`: 용기가 다른 제품. 성분이 같아 검토 대상에도 걸리지 않음
- `용표원방우황청심원` / `용표원방우황청심원(사향대체물질함유)`: 처방이 다른 제품. 성분이 달라 검토 대상에는 걸림

### 2차 규칙: 버릴 괄호만 목록으로 관리

남길 괄호를 목록으로 관리하면 목록에 없는 중요한 괄호가 조용히 과병합을 만든다. 규칙을 뒤집어 별칭 괄호(`수출명`)만 버리고 나머지는 전부 남긴다.
또한 같은 키로 묶인 허가 중 `정상`이 둘 이상이면 검토 대상으로 표시한다. 갱신이라면 이전 허가는 끝나 있어야 하기 때문이다.

결과: 허가 42,980건 → 제품 42,885개(허가 95건이 합쳐짐), 검토 대상 17개(성분 차이 9, 동시 정상 8).

### 트레이드오프

1차 규칙으로는 한 제품이었다가 2차 규칙에서 갈라진 46개 그룹을 전수 분류했다.

| 분류 | 그룹 수 | 예 |
|---|---|---|
| 갈라지는 게 맞음 | 30 | 바이알/앰플, 프리필드, 단회용, 트리트먼트·컨티뉴에이션 코오스 A~F(12종), 초기·유지요법, 소아용·성인용, 사향대체물질함유(우황청심원 10개) |
| 놓친 갱신 | 15 | 성분명 괄호 추가·삭제(네시나액트·네시나메트 5개, 이달비클로 2개 등), 염 표기 변경(알림타 2개, 리피듀엣, 디에타민의 펜터민염산염/염산펜터민) |
| 애매 | 1 | 포시진정10밀리그램 `(다파글리플로진시트르산)` / `(다파글리플로진)`. 염 변경이면 별개 제품 |

과병합 30개 그룹을 막는 대신 갱신 15개 그룹을 별개 제품으로 남긴다.
놓친 갱신을 기계적으로 가려낼 방법은 찾지 못했다. "이전 허가가 끝났으면 합친다"는 규칙은 나제론·아이델라처럼 이전 허가가 만료됐는데도 용기로 갈라져야 하는 사례에서 틀린다.
잘못 쪼개진 제품은 나중에 합칠 수 있지만, 잘못 합쳐진 제품은 어느 허가가 어느 제품이었는지 되돌릴 근거가 남지 않으므로 이 방향을 택한다.

### 참고: 동시 정상 기준으로 걸린 8개

이 중 5개가 알프라졸람, 펜터민, 옥시코돈, 날부핀, 프로포폴 성분 품목이다. 같은 이름의 허가가 동시에 유효한 이유는 데이터만으로 알 수 없어 검토 대상으로 남긴다.

## 5. 파이프라인 결함과 수정

### 적재 실패 기록이 롤백과 함께 사라졌다

적재와 수집 이력(`ingest_log`)이 같은 트랜잭션이어서, 적재가 실패해 롤백되면 `running` 행과 `failed` 기록이 모두 사라졌다. 실패를 추적하려고 만든 이력이 실패할 때만 남지 않는 구조였다.
이력 전용 autocommit 커넥션을 분리하고, `success`는 적재 커밋 이후에 기록하도록 순서를 맞췄다.

### 실패 경로의 버그는 정상 실행으로 드러나지 않았다

예외 처리 블록의 `finish_batch` 호출에서 괄호가 어긋나 인자가 전달되지 않았다. 정상 경로에서는 실행되지 않는 코드라 적재가 성공하는 동안에는 드러나지 않는다. 목(mock)으로 실패를 주입해 확인했다.

### 승인받지 않은 구버전 API를 호출하고 있었다

활용신청은 허가 08·회수 05인데 설정에는 07·04가 들어 있었다. 구버전은 예고 없이 폐기될 수 있어 교체했고, 교체 전후 배치의 필드 구성이 같은 것을 확인했다.
`.env.example`에 엔드포인트를 명시해 버전을 저장소에서 추적한다.

## 6. 알려진 한계

- 원천에서 사라진 허가·회수는 반영하지 않는다. 매 배치 전량 수집이지만 변환은 upsert라 삭제를 감지하지 않는다.
- raw 테이블은 배치마다 계속 쌓인다. 보존 기간 정책이 없다.
- 제품 키 규칙상 15개 그룹의 갱신이 별개 제품으로 남는다(4절).
- `review_needed` 제품을 사람이 검토하고 결과를 반영하는 절차는 없다.
